# gRPC Notify 广播推送设计

## 目标

为 QQBot gRPC 服务新增 `Notify` 接口。调用方仅提供消息内容；服务端自动向所有已开启定时推送的群聊和私聊订阅者发送该消息，不要求调用方提供群号或 QQ 号。

## 接口契约

在 `protocol/qqbot.proto` 的 `QQBotService` 中新增：

```proto
rpc Notify(NotifyReq) returns (Resp) {}

message NotifyReq {
  string content = 1;
}
```

`NotifyReq` 不包含收件人字段，防止调用方误将此接口用作单播。现有 `SendMsg` 的字段、行为和兼容性保持不变。

## 处理流程

1. `Notify` 从 `CQBot` 持有的持久化 `reportState` 读取群聊与私聊的定时推送订阅者快照。
2. 服务端通过现有 QQ 消息发送路径，向每个群聊订阅者和私聊订阅者发送相同的 `content`。
3. 一个收件人的发送失败不会中断对其他收件人的发送。
4. 不修改订阅状态，也不将消息正文写入错误日志。

## 返回与日志语义

- 没有订阅者时，RPC 正常返回，且 `Resp.message` 精确为 `没有可推送的订阅者`。
- 至少一个收件人发送成功时，RPC 正常返回，即使其余收件人发送失败。
- 每个失败必须写入服务端日志，包含收件人类型（群聊或私聊）、收件人 ID 和底层错误原因；不得记录推送内容。
- 存在订阅者但全部发送失败时，RPC 返回错误。

## 代码边界

- `protocol/qqbot.proto`：声明 RPC 和请求消息。
- `protocol/pb/qqbot_pb/`：更新由 protobuf 生成器产生的 Go / gRPC 绑定。
- `bot_service/`：实现 `Notify`，负责订阅快照、逐个投递、结果聚合及失败日志。
- `coolq/`：如现有可见 API 不足，仅添加一个最小导出方法以提供订阅者快照和统一的单次消息发送；不改变定时任务逻辑。

## 验证

测试应覆盖以下行为：

1. 同时向群聊和私聊订阅者广播。
2. 部分发送失败时仍正常返回，并记录每个失败的目标与原因。
3. 没有订阅者时返回成功及指定提示。
4. 存在订阅者但全部发送失败时返回 RPC 错误。
5. 既有 `SendMsg` 行为不变。
